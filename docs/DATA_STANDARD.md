# Data standard for the model catalog

For the people who add models and facts. The database enforces most of this; anything it rejects
comes back with a message saying why.

## What a fact is

One row in `capabilities` is one fact about one model: a capability **name** from the vocabulary
below, a **value** in that capability's format, and where it came from.

- **Every fact needs a source.** Add the page or API response to `sources` first
  (`source_type`: `official_docs`, `provider_api`, `scraped` or `manual_review`) and point the fact at it.
- **New facts are `unverified`.** A person who has checked the fact against its source sets
  `verification_status = 'verified'` and `last_verified_at` (the database refuses `verified` without a date).
  Scraped or synced facts stay `unverified` until someone confirms them.
- **Unknown means no row.** If you don't know whether a model has a capability, add nothing. The agent
  then says "not recorded". Never enter a guess, and never enter `false` to mean "don't know".
- **Price and API availability are facts too** (`pricing`, `api_available`), with sources like any other.
- **`models.description` is display text only.** The agent never makes claims from it, so anything a user
  might ask about belongs in a fact, not the description.

## Names and formats

- Use only names defined in `capability_definitions`. The database rejects any other name, so a typo or
  a near-duplicate (`voiceover_languages` next to `output_languages`) cannot be inserted.
- Values must match the definition's type. Lists hold distinct strings, at least one.
- Languages are ISO 639-1 two-letter codes in lowercase: `hi` for Hindi, `en` for English, `ta` for
  Tamil. The full list is in the `language_codes` table.
- `pricing` is an object: `{"currency": "USD", "unit": "second of video", "amount": 0.05}`. Use
  `"tiers": [{"label": "...", "currency": ..., "unit": ..., "amount": ...}]` when there are several prices.
  Copy the provider's own unit; don't convert.

## Adding a capability name

Propose it to the owner first, then add it in a **new migration** under `supabase/migrations/` (never edit
an applied one), so every environment has the same vocabulary. Then run `python scripts/data_standard.py`
to refresh the table below; a test fails if this document and the migrations disagree.

Before adding a name, check whether an existing one already covers it.

## Vocabulary

| `api_available` | `true` or `false` | - | true if the model can be called through a public API, false if it cannot. |
| `pricing` | a JSON object | - | Price as published by the provider.
